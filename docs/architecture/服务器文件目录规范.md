

# 空间组学项目服务器目录规范 v0.2

## 一、总体设计原则

项目采用 **以 Run（一次完整实验运行）为核心** 的目录管理方式。

核心原则：

1. **一次 Run 对应一个独立目录**，完整保存输入、配置、中间结果、最终结果和日志。
2. **原始数据统一存储**，不同 Run 可以引用同一份原始数据，避免重复占用磁盘。
3. **不同 Run 的运行文件相互隔离**，方便追踪、复现、清理和归档。
4. **代码与数据分离**：GitHub 管理代码，服务器数据目录管理数据和实验记录。
5. **运行记录可追溯**：记录算法版本、Git Commit、镜像版本、运行参数及状态。

## 三、一级目录职责

| 目录 | 主要用途 | 管理原则 |
|---|---|---|
| `datasets/` | 存储原始空间组学数据 | 原则上只读，不重复复制 |
| `runs/` | 管理所有实验运行 | 每次运行创建独立目录 |
| `shared/` | 存储多次运行共享的资源 | 统一管理与复用 |
| `incoming/` | 接收成员提交的临时文件 | 定期整理和清理 |

### 3.1 datasets：数据集中心

统一保存不同平台的原始数据。

例如：

- Xenium
- Stereo-seq
- Visium HD
- CosMx
- MERFISH

管理要求：

1. 原始数据原则上不可修改。
2. 每份数据集分配唯一的 Dataset ID。
3. 每份数据集保存对应的元信息。
4. 不同 Run 可以引用同一份 Dataset。
5. 对重要数据保存版本信息或校验值，保证可复现性。

### 3.2 runs：实验运行中心

这是整个目录系统的核心。

每执行一次完整工作流，就创建一个新的 Run。

例如：

- `run_001`：Xenium 数据 + STINR 分割 + 下游分析。
- `run_002`：同一份 Xenium 数据 + Bering 分割 + 下游分析。
- `run_003`：STINR 算法使用不同参数重新运行。

**一个 Run 不一定只运行一个算法，而是对应一次完整的工作流执行。**

### 3.3 shared：共享资源

保存可供不同 Run 复用的资源。

主要包括：

- `references/`：参考基因组、注释文件等。
- `container-archives/`：临时保存离线传输的 Docker 镜像归档文件。

Docker 镜像导入 Docker Engine 后，由 Docker 自身管理，`.tar` 归档文件可按需删除。

### 3.4 incoming：临时交付

用于成员提交不适合直接放进 GitHub 的文件。

例如：

- 临时测试数据
- 大型模型文件
- 外部交付的数据材料

正式纳入项目后，应移动到合适的位置，不应长期堆积。

## 四、单个 Run 的详细设计

### 4.1 input/

记录本次运行使用的数据源。

例如：

```text
input/
└── dataset.yaml
```

不要求把大型原始数据复制进来。

可以通过：

- 数据路径引用
- 符号链接（Symbolic Link）
- Docker Bind Mount

访问 `datasets/` 中的数据。

注意：引用的原始数据应保持不可变，并记录其版本。

### 4.2 intermediate/

存储本次运行中需要保留的中间计算结果。

例如：

```text
intermediate/
├── preprocessing/
└── segmentation/
```

用于保存数据转换、质量控制和算法处理的中间产物。

与 `work/` 的区别：

- `intermediate/`：计划保留和检查的中间结果。
- `work/`：Nextflow 的任务执行目录与缓存。

### 4.3 output/

存储本次运行的最终分析结果。

```text
output/
├── segmentation/
├── analysis/
└── figures/
```

分别对应：

- `segmentation/`：细胞分割结果。
- `analysis/`：统计分析、评价指标等。
- `figures/`：可视化图像及报告。

### 4.4 work/

存储 Nextflow 的执行缓存及任务工作文件。

主要用途：

- 保存任务执行过程中的文件。
- 支持任务缓存复用。
- 支持符合条件时通过 `-resume` 继续工作流。

注意：

**不能在需要续跑时随意删除 `work/`。**

### 4.5 logs/

保存本次运行的日志。

包括：

- 算法运行日志
- 工作流执行日志
- 错误信息
- 任务状态记录

便于后续排查和复现实验。

### 4.6 config.yaml

保存本次运行使用的配置参数。

例如：

```yaml
dataset_id: xenium_001

workflow: spatial_segmentation

algorithm:
  name: stinr

resources:
  cpus: 8
  memory: "32 GB"
  gpus: 1
```

以上只是配置格式示例，最终字段应与实际工作流参数接口保持一致。

### 4.7 metadata.json

记录本次运行的元信息。

例如：

```json
{
  "run_id": "run_001",
  "dataset_id": "xenium_001",
  "workflow": "spatial_segmentation",
  "algorithm": "stinr",
  "git_commit": "<实际提交哈希>",
  "container_image": "<实际镜像标识>",
  "status": "completed",
  "started_at": "<实际开始时间>",
  "finished_at": "<实际结束时间>"
}
```

主要记录：

- Run ID
- 数据集 ID 和版本
- 工作流名称
- 算法名称
- Git Commit
- Docker 镜像版本或 Digest
- 运行状态
- 开始与结束时间

正式实现时，这些信息应由工作流自动生成，避免手动填写出错。

## 五、Run 命名规范

初期采用：

```text
run_001
run_002
run_003
```

要求：

1. 每个 Run ID 必须唯一。
2. 不得覆盖其他 Run。
3. 失败的 Run 也应该保留必要的元信息和日志。
4. 失败任务的恢复执行与创建新 Run 应明确区分。

后续可考虑增加日期：

```text
20261118_segmentation_001
20261118_segmentation_002
```

目录名称用于识别运行，具体的算法、数据、参数和版本信息统一记录在 `metadata.json`。

## 六、GitHub 与服务器的数据分离

### 6.1 GitHub：代码管理

主要负责：

- 数据处理代码
- 算法封装
- Dockerfile
- Nextflow 工作流
- 下游分析代码
- 配置模板
- 测试和文档

服务器部署代码副本规划为：

```text
/home/yuhaoran/projects/spatialbio/
```

正式部署时，从 GitHub 获取经过验证的代码版本。

### 6.2 Dataset：数据与运行管理

```text
/Dataset/spatial-project/
```

负责：

- 原始数据
- 运行参数与元信息
- 中间结果
- 最终分析结果
- 工作流缓存
- 运行日志

**GitHub 负责定义怎么计算，Dataset 负责保存计算使用的数据、过程及结果。**

## 七、基础目录创建

目前只创建基础目录，不提前建立 `run_001` 等实验目录。

### 7.1 创建目录

```bash
mkdir -p /Dataset/spatial-project/{datasets,runs,shared/references,shared/container-archives,incoming}
```

#### 命令与参数解释

| 内容 | 类型 | 含义 |
|---|---|---|
| `mkdir` | 命令 | Make Directory，创建目录 |
| `-p` | Option | `--parents`，创建缺失的父目录，目录已存在时不报错 |
| `/Dataset/spatial-project/` | 路径 | 项目共享根目录 |
| `{...}` | Bash 语法 | Brace Expansion，花括号展开 |
| `,` | 分隔符 | 分隔多个待创建路径 |

花括号展开示例：

```bash
mkdir -p demo/{a,b,c}
```

等价于：

```bash
mkdir -p demo/a demo/b demo/c
```

### 7.2 检查目录

```bash
find /Dataset/spatial-project -maxdepth 3 -type d
```

#### 命令与参数解释

| 内容 | 类型 | 含义 |
|---|---|---|
| `find` | 命令 | 搜索文件和目录 |
| `/Dataset/spatial-project` | 路径 | 搜索起点 |
| `-maxdepth` | Option | 限制搜索深度 |
| `3` | 参数值 | 最多搜索到起点以下第三层 |
| `-type` | Option | 按文件类型筛选 |
| `d` | 参数值 | Directory，仅匹配目录 |

预期目录：

```text
/Dataset/spatial-project
/Dataset/spatial-project/datasets
/Dataset/spatial-project/runs
/Dataset/spatial-project/shared
/Dataset/spatial-project/shared/references
/Dataset/spatial-project/shared/container-archives
/Dataset/spatial-project/incoming
```

## 八、文件权限与安全要求

目前 `/Dataset` 根目录权限为 `777`。

虽然 `/Dataset/spatial-project` 已经通过 ACL 授权给项目成员，但父目录权限仍然存在安全风险。

需要注意：

1. 普通非授权用户无法直接读取受保护的项目子目录。
2. 由于 `/Dataset` 对所有用户开放写入且没有 sticky bit，其他用户仍可能重命名或删除其中的目录项。
3. 后续需要与服务器管理员协调修复父目录权限。
4. 不应随意对共享目录执行 `chmod -R 777`。
5. Docker 管理权限与共享文件访问权限应独立管理。
6. 具有 root 权限的管理员仍然可以访问项目文件。

## 九、后续自动化要求

未来接入 Nextflow 后，应尽量自动完成：

1. 为每次正式执行生成唯一 Run ID。
2. 创建本次 Run 的目录结构。
3. 保存本次运行使用的数据引用。
4. 记录配置参数和代码版本。
5. 将 Nextflow 工作目录设置到当前 Run 的 `work/`。
6. 将算法输出统一收集到当前 Run 的 `output/`。
7. 保存日志及运行状态。
8. 生成和更新 `metadata.json`。
9. 支持失败恢复、运行记录查询及结果复现。

对于尚未建立 Run ID 的临时调试任务，可以使用独立测试区域，避免污染正式运行记录。

## 十、最终架构规范

| 项目 | 规范 |
|---|---|
| 服务器项目根目录 | `/Dataset/spatial-project/` |
| 核心组织单位 | Run |
| 原始数据 | `datasets/` |
| 实验运行 | `runs/run_xxx/` |
| 公共资源 | `shared/` |
| 临时交付 | `incoming/` |
| 代码版本管理 | GitHub |
| 工作流编排 | Nextflow |
| 容器运行环境 | Docker |
| Run 目录生成 | 后续由工作流自动完成 |
| 结果可复现性 | 参数、数据版本、代码版本、镜像版本与日志共同保证 |

### 核心总结

> **GitHub 管理代码版本，Dataset 管理科研数据与实验记录，Run 是一次完整科研计算的独立管理单位。**
>
> 每次实验拥有独立的输入引用、中间结果、最终结果、日志和元信息；公共原始数据统一存储，通过明确的数据引用实现复用。

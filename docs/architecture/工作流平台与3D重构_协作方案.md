# 空间组学项目：工作流平台与 3D 重构协作方案

**版本：** v1.0\
**适用对象：** 项目全体成员\
**人员范围：** 六名项目成员；项目负责人不计入六名成员\
**总体原则：** 两条路线并行推进、目标独立、接口协作、实现解耦。

------------------------------------------------------------------------

## 一、项目总体架构

项目分为两条并行技术路线：

1.  **路线一：工作流平台**------负责数据读取与标准化、算法接入、任务编排、异常捕获、运行管理和结果追溯。
2.  **路线二：3D
    重构与科研分析**------负责空间组学平台研究、算法筛选、需求驱动的数据分析、三维重构及交互展示。

两条路线共享标准化数据、必要的算法结果和元数据，但不互相依赖内部实现。工作流平台不负责三维渲染和手势交互；3D
模块不负责 Nextflow 的任务调度和平台级异常管理。

## 二、路线一：工作流平台

工作流平台由数据层、算法层、工作流编排、异常捕获与回溯四名成员协作完成。

### 阶段一：科研调研与需求输入

#### 科研1：空间组学平台调研

主要任务： - 调研 Stereo-seq、Xenium、CosMx、MERFISH、Visium HD
等平台。 - 明确各平台能够提供的数据类型、分辨率和数据粒度，例如
Bin、Spot、Cell、Transcript。 -
调研图像、空间坐标、表达矩阵、细胞边界等数据的组织形式。 -
确认平台是否提供真实三维坐标、多张组织切片及其空间关系。

交付物： - `platform_comparison.md`：平台与数据特性对照表。 -
`platform_data_mapping.md`：平台原始字段与数据类型映射。 -
`platform_data_samples/`：代表性样例数据或样例目录说明。

#### 科研2：算法调研与筛选

主要任务： - 搜集空间组学领域主流开源算法。 -
按图像预处理、细胞分割、转录本分配、空间分析等类别整理。 -
收集论文、GitHub 地址、许可证和版本信息。 -
初步调查算法输入输出、运行环境及硬件要求。 -
区分工作流平台使用的通用分析算法和 3D 重构专用算法。

交付物： - `algorithm_catalog.md` - `algorithm_comparison.xlsx` -
论文、开源仓库及许可证清单。

**算法去向：**
细胞分割、转录本分配等通用计算算法，进入工作流平台接入流程；三维配准、重构、渲染等专用算法，由
3D 方向评估。若 3D 算法需要作为可复用计算任务由 Nextflow
调度，再按算法接入规范封装；纯展示端的交互与渲染逻辑由 3D 模块自行实现。

### 阶段二：数据层与算法层协作

核心原则：**算法层提出数据需求，数据层提供符合要求的数据；算法层不得随意要求数据层拆解或重写算法内部计算步骤。**

#### 数据层职责

-   根据科研1提供的平台清单读取原始数据。
-   解析 TIFF、CSV、Parquet、H5AD 等实际使用的数据格式。
-   统一字段名称、数据类型、维度和必要的元数据。
-   将平台数据转换为项目内部约定的格式。
-   执行文件完整性、字段存在性、类型和维度等基础检查。
-   根据算法层提交的需求执行约定的基础预处理。
-   输出标准化数据及算法就绪数据。

#### 关于 QC 的明确声明

**前期输入数据已经过筛选，属于相对干净的数据，因此前期不需要项目负责人参与日常数据准备，也不要求数据层开展空间组学科学
QC。**

前期只开展基础数据有效性检查，例如： - 文件是否存在、是否能够读取； -
必需字段是否存在； - 数据类型和维度是否符合接口约定； -
必要的文件结构是否完整。

空间组学科学 QC
由项目负责人负责，后续根据实际数据情况制定指标、规则和验证流程。基础格式检查不能替代科学
QC。

  ------------------------------------------------------------------------------------------
  检查类型                负责人                  作用
  ----------------------- ----------------------- ------------------------------------------
  基础数据有效性检查      数据层                  文件、字段、格式、类型、维度是否符合要求

  空间组学科学 QC         项目负责人              评估数据及分析结果的科学质量
  ------------------------------------------------------------------------------------------

#### 算法层向数据层提出需求

算法层完成算法复现后，分析算法需要的输入文件、字段、格式、维度、单位和预处理要求，提交： -
`input_spec.yaml` - `preprocessing_requirements.md`

示例：

``` yaml
algorithm: nucleus_segmentation

inputs:
  - name: nucleus_image
    format: TIFF
    required: true

  - name: image_metadata
    format: JSON
    required: true

preprocessing:
  - image_format_conversion
  - metadata_extraction
```

数据层据此判断现有数据是否满足要求；如不满足，双方协商必要的外部预处理并共同验证。

**边界要求：**
算法内部的归一化、特征提取、模型内部图构建等步骤原则上保留在原算法中。只有经算法层确认不会改变算法语义的步骤，才交由数据层提前处理。必须避免重复预处理。

### 阶段三：算法封装与异常规范并行建设

本阶段由算法层和异常捕获与回溯成员并行推进。

#### 3.1 异常捕获成员：制定统一错误码

  统一错误码            含义       典型场景
  --------------------- ---------- ----------------------------
  `INPUT_ERROR`         输入错误   文件不存在、无法读取
  `DATA_ERROR`          数据错误   数据结构或格式异常
  `PARAMETER_ERROR`     参数错误   参数缺失或不合法
  `ENVIRONMENT_ERROR`   环境错误   缺少依赖、环境不兼容
  `RESOURCE_ERROR`      资源错误   内存、显存、磁盘资源不足
  `ALGORITHM_ERROR`     算法错误   算法内部计算失败
  `OUTPUT_ERROR`        输出错误   输出文件缺失、损坏或不完整
  `EXECUTION_ERROR`     执行错误   进程启动失败、异常终止
  `UNKNOWN_ERROR`       未知错误   证据不足，无法可靠判断

#### 3.3 Wrapper 与 JSON 统一接口

采用两层 Wrapper：

**算法专用 Wrapper（算法层负责）** -
将项目统一输入映射为算法原生输入。 -
接收工作流传入的参数、输入路径和输出路径。 - 调用原始算法。 -
处理算法自身能够捕获的异常。 - 按约定返回运行状态。

**通用 Runtime Wrapper（异常捕获成员负责）** - 启动算法进程。 - 收集
Exit Code、stdout、stderr 和可获取的 Signal。 - 检查输出文件完整性。 -
根据算法专属映射规则识别错误。 - 生成统一 JSON 任务报告。

``` mermaid
flowchart TD
    A["Nextflow"]
    B["通用 Runtime Wrapper"]
    C["算法专用 Wrapper"]
    D["原始算法"]
    E["Exit Code / stdout / stderr / Signal"]
    F["算法专属错误映射"]
    G["统一错误码"]
    H["统一 JSON 报告"]

    A --> B --> C --> D
    D --> E --> F --> G --> H
    H --> A
```

统一 JSON 示例：

``` json
{
  "schema_version": "1.0",
  "run_id": "run_001",
  "task_id": "segmentation_001",
  "sample_id": "sample_001",
  "algorithm": {
    "name": "nucleus_segmentation",
    "version": "1.0",
    "language": "Python"
  },
  "execution": {
    "status": "FAILED",
    "exit_code": 1,
    "signal": null,
    "attempt": 1
  },
  "error": {
    "error_code": "INPUT_ERROR",
    "original_error_type": "FileNotFoundError",
    "message": "Input file does not exist",
    "retryable": false
  },
  "diagnostics": {
    "stdout_path": "logs/stdout.log",
    "stderr_path": "logs/stderr.log",
    "traceback_path": "logs/traceback.log"
  }
}
```

建议成功和失败都采用统一的任务结果 JSON 外层结构。成功时 `status` 为
`SUCCESS` 并记录正式输出；失败时 `status` 为 `FAILED`
并记录错误类别及诊断信息。

**重要：JSON
是结构化报告，不是进程退出状态的替代品。任务失败必须返回非零退出码，才能让
Nextflow 正确识别失败。** 即使退出码为
0，也必须执行输出完整性验证；如果必需输出缺失，应判定为 `OUTPUT_ERROR`。

错误映射必须有证据。无法可靠判断的错误归入
`UNKNOWN_ERROR`，不得仅凭模糊日志关键词推断错误类别。

### 阶段四：工作流编排与异常链路共同设计

工作流编排成员和异常捕获成员从 Pipeline 设计阶段就共同参与，不应等
Pipeline 完成后再补异常管理。

#### 工作流编排成员职责

-   根据算法输入输出规范编写 Nextflow Process。
-   使用 Channel 传递文件和任务元数据。
-   根据输入输出关系构建 DAG。
-   设计分支、汇合、条件执行。
-   管理参数和运行配置。
-   实现断点续跑。
-   将统一运行接口接入各 Process。

#### 文件驱动 Pipeline 示例

``` mermaid
flowchart TD
    A["原始数据"]
    B["DATA_PREPROCESS"]
    C["DATA_VALIDATION"]
    D["NUCLEUS_SEGMENTATION"]
    E["TRANSCRIPT_ASSIGNMENT"]
    F["DOWNSTREAM_ANALYSIS"]

    B --> C --> D --> E --> F

    D -. "日志与错误报告" .-> X["统一异常管理"]
    E -. "日志与错误报告" .-> X
    F -. "日志与错误报告" .-> X

    X --> Y["运行追溯与错误汇总"]
```

Nextflow 的核心概念：

  概念       作用             项目中的对应内容
  ---------- ---------------- -----------------------
  Process    定义独立任务     细胞分割、转录本分配
  Channel    传递任务数据     图像、掩膜、细胞表
  Workflow   组织任务及依赖   完整空间组学 Pipeline

Nextflow
不会自动读取算法目录并推断运行方式。算法接口文件是契约，工作流成员需要根据契约编写
Process、Channel 和 Workflow。

#### 异常捕获与回溯成员职责

每个任务至少需要记录： - `run_id`：运行批次标识； -
`task_id`：任务唯一标识； - `sample_id`：样本标识； -
`attempt`：执行尝试次数； - 输入文件、参数和镜像版本； - stdout、stderr
和必要的 Traceback； - 统一错误 JSON； - 任务最终状态。

建议运行目录：

``` text
runs/
└── run_001/
    ├── inputs/
    ├── intermediate/
    ├── outputs/
    ├── logs/
    │   ├── preprocessing/
    │   ├── segmentation/
    │   └── assignment/
    ├── errors/
    │   ├── preprocessing_001.json
    │   ├── segmentation_001.json
    │   └── assignment_001.json
    └── reports/
        └── run_report.json
```

失败重试建议：

  错误类别              默认处理
  --------------------- ------------------------------------
  `INPUT_ERROR`         不重试，检查输入路径
  `DATA_ERROR`          不重试，修正数据
  `PARAMETER_ERROR`     不重试，修正参数
  `ENVIRONMENT_ERROR`   修复环境后再运行
  `RESOURCE_ERROR`      调整资源后视情况重试
  `ALGORITHM_ERROR`     通常不自动重试
  `OUTPUT_ERROR`        检查存储、写入和输出逻辑
  `EXECUTION_ERROR`     根据进程信号和环境证据判断
  `UNKNOWN_ERROR`       默认不自动重试，保留日志供人工诊断

Nextflow 主要依据任务退出状态和执行策略决定是否重试，不会天然理解自定义
`error.json` 的业务字段。如果需要按照 `error_code`
精细控制重试，异常捕获成员还需要实现状态桥接，将统一错误类别转换为
Nextflow 可使用的状态信息。

若容器被 OOM Killer 或 SIGKILL 直接终止，容器内程序可能来不及生成
JSON；此时需要通过 Nextflow 退出状态和外部运行日志补充诊断。

#### 双方协作边界

  工作                      工作流编排成员   异常捕获与回溯成员
  ------------------------- ---------------- --------------------------
  DAG、Process、Channel     主责             配合
  统一错误码、JSON Schema   配合             主责
  算法错误映射              配合             主责，算法层提供原始信息
  通用 Runtime Wrapper      配合接入         主责
  失败策略                  协同设计         主责错误分类策略
  断点续跑                  主责设计         配合状态恢复
  日志和错误追溯            协同             主责

### 阶段五：工作流平台验收

第一阶段至少具备： - 读取标准化空间组学数据； - 调用 Python、R、C++
等不同语言算法； - 在独立 Docker 环境中运行算法； - 按文件依赖组织
Pipeline； - 支持任务分支和汇合； - 记录任务状态和运行日志； -
捕获、分类并报告算法异常； - 实现合理的失败处理、重试和断点续跑。

第一阶段不要求完成完整的集群调度系统，也不要求将 3D 渲染集成进
Nextflow。

## 三、路线二：3D 重构与科研分析

3D
路线由科研1和科研2负责，与工作流平台并行推进。前期可以直接使用原始数据、代表性平台样例和已有标准化数据开展研究，不必等待整个工作流平台完成。

### 阶段一：数据与算法调研

  工作                 科研1   科研2
  -------------------- ------- -------
  平台数据特性         主责    配合
  获取代表性平台数据   主责    配合
  数据粒度和空间信息   主责    配合
  主流分析算法调研     配合    主责
  3D 重构算法调研      配合    主责
  算法可行性验证       配合    主责
  3D 展示需求整理      协同    协同

算法分为两类： 1.
**空间组学分析算法**：图像预处理、细胞分割、转录本分配、空间分析等，主要进入工作流平台。
2. **3D
重构专用算法**：多切片配准、三维重建、三维网格或点云生成等，主要由 3D
模块研究。

#### 支线一：需求驱动的直接数据分析

根据用户科研需求，对空间组学数据开展针对性分析，例如： -
特定基因的空间表达分布； - 不同细胞类型的空间分布； -
不同组织区域的基因表达比较； - 细胞之间的空间关系； -
不同算法结果的比较； - 针对具体研究问题开展统计分析。

科研1主要提供平台数据背景、字段含义和生物学解释；科研2主要提供分析算法、方法筛选和结果验证支持。

交付物：分析报告、分析结果数据及可视化材料。

#### 支线二：3D 重构

第一阶段明确两项核心功能。

**功能一：基因表达映射与颜色筛选** -
根据不同基因的表达情况，对细胞或空间对象进行颜色映射。 -
支持切换不同基因。 -
根据颜色或表达值范围筛选特定细胞、区域或空间对象。 -
支持仅展示选定表达区间的对象。 - 支持隐藏未选中的对象。

细胞级表达映射至少需要：

  数据字段            作用
  ------------------- ------------------------
  `cell_id`           细胞唯一标识
  `coordinates`       细胞空间坐标
  `gene_expression`   对应细胞的基因表达数据
  `cell_type`         可选，细胞类型
  `segmentation`      可选，细胞边界或形态
  `sample_id`         样本编号

必须保证基因表达数据与细胞 ID
的对应关系。如果原始数据只有转录本坐标，需要先完成转录本与细胞的对应或聚合，才能进行准确的细胞级表达映射。

**功能二：手势交互** - 通过手势控制三维组织模型放大和缩小。 -
通过手势控制三维组织旋转。 - 支持交互过程中的视角调整。 -
手势控制不得修改原始空间数据。

建议拆成两个独立模块：

1.  **手势识别模块**：识别手部动作，产生放大、缩小、旋转等控制事件。
2.  **3D 渲染交互模块**：接收控制事件，调整三维场景的相机和视角。

手势识别不应与空间组学数据处理算法耦合。更换手势识别算法时，不需要重写三维数据结构和渲染模块。

### 阶段三：3D 重构的数据条件

必须区分三维展示和真正的三维重建：

  数据情况                可以开展的工作
  ----------------------- ------------------------------------------------
  已有真实 X、Y、Z 坐标   可以直接构建三维空间展示
  多张二维组织切片        需要研究切片配准、空间对应关系和 Z 轴位置
  只有一张二维切片        可以进行二维展示，不能凭空宣称完成真实三维重建

科研1负责调查平台是否提供三维坐标或多切片数据；科研2负责研究相应的重建算法及可行性。

## 四、两条路线之间的接口与解耦原则

### 4.1 数据接口

建议维护一份项目级数据 Schema，两条路线遵守相同的数据语义和标识规范。

  数据内容         工作流平台       3D 重构
  ---------------- ---------------- --------------------
  原始平台数据     负责读取和处理   用于研究与验证
  标准化表达矩阵   负责生成         用于基因表达分析
  空间坐标         负责标准化       用于空间定位
  细胞 ID          负责统一         用于细胞查询与对应
  细胞分割结果     负责算法输出     用于形态展示
  基因表达信息     负责数据交付     用于颜色映射
  三维坐标         按数据条件保留   用于三维展示
  算法运行日志     负责记录         不负责管理

### 4.2 职责隔离

  工作内容             工作流平台           3D 重构
  -------------------- -------------------- ------------------
  数据读取与标准化     主责                 消费标准化数据
  基础预处理           主责                 提出特定数据需求
  通用算法封装         主责                 提供算法研究成果
  Docker 环境          项目负责人统筹       按需要独立管理
  Nextflow 编排        主责                 不参与
  平台级异常捕获       主责                 不负责
  需求驱动的数据分析   提供数据和算法结果   主责
  三维重建             不负责               主责
  手势交互             不负责               主责
  三维渲染             不负责               主责

**解耦原则：**
两条路线可以共享数据、算法成果和通用技术，但不应形成组织和代码上的强耦合。3D
模块可以独立开发和验收；如某个 3D 计算算法需要 Nextflow
调度，再通过标准算法接口接入，而不是将整个 3D 展示模块纳入工作流平台。

### 第一阶段最终验收要求

**工作流平台：** - 能读取标准化数据； - 能调用多语言算法； - 能在 Docker
环境运行； - 能按文件依赖组织 Pipeline； - 能记录任务状态和运行日志； -
能生成统一异常报告； - 能进行合理的失败处理和断点续跑。

**3D 重构与科研分析：** - 能根据科研需求完成一轮直接数据分析； -
能判断真实三维坐标或多切片数据是否满足重建条件； -
能按基因表达进行颜色映射； - 能按颜色或表达值范围筛选展示对象； -
能通过手势实现三维组织放大、缩小和旋转。

## 六、项目实施中的关键约束

1.  前期输入数据相对干净，数据层只负责基础有效性检查和约定的预处理；空间组学科学
    QC 由项目负责人负责，前期不要求其参与日常数据准备。
2.  算法层必须分别向工作流编排、项目负责人、异常捕获与回溯成员提交三类交付物，不得只提交源代码。
3.  算法输入输出必须通过文件契约明确，不能依赖口头约定。
4.  算法内部的关键计算步骤不得未经验证就拆给数据层。
5.  统一 JSON 报告不能替代进程退出码；失败必须返回非零退出状态。
6.  每个任务独立记录日志和错误报告，并保留运行 ID、任务 ID、样本 ID
    和尝试次数。
7.  3D
    展示与真实三维重建必须区分；缺乏真实空间依据时不得将人为添加的厚度描述为真实三维重建。
8.  两条路线共享数据标准，但保持各自独立的代码、运行方式和验收标准。

## 七、最终项目原则

**工作流平台负责把空间组学分析变成可重复、可管理、可追溯的工程流程；3D
重构负责把空间组学数据转化成可分析、可交互的科研成果。**

两条路线拥有共同的数据基础，但具有独立的开发目标、技术实现和验收标准。通过标准化数据接口与算法结果交付实现协作，而不是相互嵌套。
